01 · Proposed experience

Read the story. Follow the evidence.

The center pane contains only the authored briefing: prose, diagrams, and concise behavior examples. A compact outline sits on the left. Source code, questions, selected-context chips, and review metadata live in the right pane or their existing dedicated tabs. Opening a tool never inserts a panel into the document.

02 · Product contract

A coherent first release

Included

  • A persistent Briefing tab with repository, branch, title, and captured-source context.
  • Summary and observable behavior, followed by a few design-led sections with interleaved prose, diagrams, and concise behavior examples. Source citations open code in the right pane.
  • Existing architecture/boundary, sequence, state-machine, data-model, call-flow, and domain diagrams when available, validated, enabled, and useful. Each included diagram family supports element selection and its corresponding saved source snippets through the shared evidence adapter. Use an architecture map to explain responsibility boundaries and the contracts crossing them when this adds understanding. No mandatory diagram count.
  • One contextual right pane with a named inspection target, its evidence, and a collapsible question composer beneath it. There are no Source / Questions tabs. Sequence diagrams show all steps’ code vertically in authored order; selecting a message reveals and highlights its matching card. Other diagram types group snippets by their own elements—components, states, transitions, entities, relationships, calls, or domain concepts—and synchronize diagram/card selection in both directions. Questions can include sections, selected text, whole diagrams, and supported elements; combine or remove context chips within that pane. Opening the full Changes view is an explicit secondary action.
  • Revision awareness, old-session fallback, resume, and Markdown / HTML export.
  • Findings and checks stay in their existing Findings / Pull request views. Effort and lightweight review metadata move to a collapsed Review details area in the right pane; none is appended to the central narrative.

Deliberate limits

  • No document editor, freeform whiteboard, custom layout engine, or new diagram language.
  • No additional PR provider integrations or automatic crawling of linked systems.
  • No mandatory five-section template: include only the questions supported by the change. A small fix can be mostly text.
  • No claim of runtime verification from diagrams, illustrative inputs, or test source alone.
  • No separate agent call on the normal initial path. Startup continues preparing the first code stop before opening the browser; earlier opening can follow later.

Tabs: add Briefing and rename the existing visible Diff label to Changes, as agreed. Keep the underlying diff view identity, file navigation, Shiki/Monaco choices, existing links, review actions, and tour controls. There is one code-review workspace. Update visible labels and accessible names consistently. The existing Briefing tab is the way back from Changes; do not add a duplicate “Back to briefing” button. Switching tabs restores the reader, inspected item, source-list position, diagram selection, and composer/draft state without advancing the tour. Activating an already-selected tab is a no-op for reading position. Desktop keyboard focus stays with the activated tab; on mobile, reopening an active side sheet follows its dialog focus rules.

Pane ownership is a product rule: left = section navigation; center = authored briefing; right = source evidence, questions, and review tools. Code previews, question forms, context chips, loading/errors for those tools, findings lists, and effort estimates never render inside the center document. Small source citations and selection affordances may open the right pane. Narrative discussion and diagrams of design boundaries belong in the document; automated review status stays outside it. Same-page actions use plain labels without external-link arrows. The pane header supplies close/collapse; do not add a redundant “Back to reading” action inside the composer.

Landing behavior: generated reviews open Briefing when the existing show-briefing preference is enabled. Ordinary diff-only launches still work; the Briefing tab offers an explicit “Generate briefing” action through the current tour setup. Resume restores an explicitly selected view. Legacy intro=1 links select Briefing.

Preference compatibility: “Show briefing” becomes “Open reviews in Briefing”; the tab remains accessible. Keep the diagram content toggles. Map existing attention and effort toggles to the supporting right-pane Review details area; they never inject content into the center. Narrative section order is authored by the generator; retire the old drag-to-reorder controls, accept persisted legacy fields, and preserve their order only among supporting entries in the legacy right-pane fallback. Legacy sessions follow the same clean-center rule.

No unintended review progress: reading, expanding a diagram, and inspecting evidence do not mark files reviewed, move the current stop, or change review decisions. Only an explicit “Start / continue code tour” action navigates the tour.

Data contract and validation

Add an optional, versioned briefing to TourOutline. Keep the existing BriefingSection preference type separate from the new document section type. Candidate agent output contains prose and references; the server supplies identity, timestamps, fingerprints, and exact code excerpts.

Evidence references captured PR text, task/issue material, or an exact path, side, and line range. Code evidence stores the validated snippet and blob identity; the model never supplies executable source as the excerpt. Examples state whether they come from source/tests or are illustrative. A SourceRefBlock is a compact citation whose content opens in the right pane. Diagram blocks reference existing validated artifacts, with a caption explaining their role. Retain the artifact fingerprint, displayed Before/After/Changes view, stable element IDs, and existing source mappings; embedding a diagram must preserve its interactive source and walkthrough capabilities. A diagram is not reduced to a static image.

One diagram-to-evidence contract: all included diagram families use the same validated element bindings and captured-source reader. Keep family-specific adapters for identity and meaning. Sequence messageSources and native call-flow locations already provide exact references; architecture and adaptive diagrams need new optional elementSources proposals in their outline output. Each proposal identifies an authored node/message/relationship and bounded path/side/line-range references. The server validates the authored element, carries explicit identity mappings through rendering, and resolves references against captured blobs. Retain existing saved sequence/call-flow fields and adapt them to this contract rather than migrating or regenerating valid evidence. File lists, component names, node roles, and nearby code are not element-source mappings.

DiagramRefBlock {
  id, artifactId, artifactFingerprint, comparisonView, caption
  family                               // sequence / architecture / lifecycle / data-model / call-flow / domain
  elementEvidence: {                   // validated and hydrated by the server
    kind: "node" | "edge" | "message"
    elementId                          // exact adapter element ID in this view
    evidenceIds: string[]               // saved code or document records, up to 8 per element
  }[]
}

artifactId identifies the captured logical diagram, including native diagrams without Archify HTML. An adapter maps that identity and the selected view to the exact rendered IDs. Keep bindings with the captured artifact/evidence identity; do not reconstruct them in the browser. Validate element existence in the selected Before/After/Changes view and reject ambiguous or stale IDs. Preserve authored-to-rendered IDs for states, entities, and components; identify repeated relationships by their authored occurrence and captured fingerprint, never by caption alone. Renderer-generated layout decorations and synthetic start/end markers have no implied code. An element can reference several locations and a source can support several elements. Unknown/external elements remain selectable with an explicit “No linked code” state. Invalid optional bindings leave the valid diagram readable without an invented association. Legacy artifacts without bindings still load.

Initial ceilings: 12 sections, 60 blocks, 40 evidence references, and 24,000 prose characters per briefing; right-pane source previews show at most 30 lines / 8,000 characters per excerpt. Prefer a substantially smaller document. Validate unique IDs, target existence, bounded content, captured-source ranges, and each block’s shape. Render constrained Markdown and existing diagram output; raw agent HTML is not part of the contract.

Boundary diagrams: there is no dedicated boundary type in the current contract. Use a supported architecture artifact, framed by its caption as a responsibility / contract view: name the owners and label what crosses between them. Shape one of the existing behavior or implementation maps to serve this explanation when appropriate; do not require another generated map or introduce a separate diagram family. The present architecture adapter supports components and labelled relationships, not arbitrary nested boundary containers. The mock uses this vocabulary. Show process, trust, transaction, or deployment boundaries only when the source establishes them; a module split alone proves none of those. Keep requested-but-unverified guarantees in adjacent attributed prose, not as implemented components or enforcement marks. Existing diagram preferences and no-diagram fallbacks still apply. Boundary components participate in the same component-to-code binding and selection behavior as the architecture views.

Reference validation establishes that evidence exists, not that a claim is true. Prompt instructions, honest provenance labels, human-readable citations, and evaluation examples address that distinction. Unsupported intent is omitted or explicitly labeled as unknown.

Generation, freshness, and recovery

Intent inputs: extend AgentClient.createOutline() beyond its current linked-issue argument to receive a bounded snapshot of PR title/body, available linked issue, reviewer task, and source-backed domain context. Attribute sources individually; preserve disagreements instead of silently merging them. Treat embedded instructions as source material. Local reviews can infer behavior from code without inventing author intent.

Initial generation: request briefing sections and optional diagram element-source references in the existing outline call, then validate references against the final accepted diagrams and steps. Invalid optional briefing output must not discard a valid code tour or restart all analysis. Retain valid sections when safe; otherwise serve a concise fallback from the existing summary and validated artifacts, labeled as a basic overview.

Regeneration: add a focused POST /api/briefing/regenerate operation. It reuses the existing agent transport and tour.outline prompt kind with an explicit briefing-only JSON contract. It does not replace phases, findings, or the current stop. Update the bundled attached-agent instructions to recognize that prompt alongside the existing full-outline and finding-audit prompts. Commit only if the captured code and intent fingerprints still match; a failed or superseded result leaves the last valid briefing available.

Revision semantics: use captured comparison identity plus an intent-content hash, not the session’s general revision counter. A new comment must not invalidate the document. Changes to code, comparison scope, relevant PR/task content, or a referenced diagram invalidate affected evidence; conservatively label the document outdated in v1. Keep the old snapshot visible, require explicit refresh, and never resolve stale line numbers into current code. Captured snippets remain readable; unavailable source navigation explains why.

Resume and export: accept older sessions without this optional field. Validate new fields on both ingestion and restore; isolate an invalid optional briefing without losing the valid tour. HTML and Markdown exports include the narrative, captions, citations, source evidence, and freshness state. HTML keeps evidence in a side inspector; Markdown keeps longer excerpts in an evidence appendix linked from the prose. Exported diagrams use the existing export renderers. Existing “omit diagrams/findings” choices remain effective. Closed/offline reviews remain readable and expose no live question or regeneration actions.

04 · Implementation sequence

Six milestones, each with a concrete exit.

Implement in this order. The feature is ready to ship after the compatibility, export, and browser checks in milestone six—not just after the new view looks complete.

1 · Contract and fixtures

Define the document and source identities.

Add types and a focused validation/hydration module. Build deterministic fixtures for a small fix, a change across several files, missing intent, and a documentation-only proposal. Include an old session with no briefing, formatted/repeated text selections, a source-linked sequence with multiple anchors, and an unlinked message. Include an architecture map of responsibility boundaries with explicit crossing contracts, exact component-source bindings, a component with multiple anchors, and an unlinked/external component. Cover repeated labels, one source shared by components, old-side evidence, and a claimed trust or process boundary lacking evidence. Add representative fixtures for lifecycle states/transitions, data entities/relationships, call nodes/edges, and domain concepts/glossary sources, including unlinked elements in each family.

Exit: valid documents round-trip; duplicate IDs, bad targets, oversized output, and fabricated source ranges fail predictably. Proposed behavior stays distinct from implemented behavior.

2 · Generation and persistence

Produce the narrative from the captured review.

Extend intent inputs, outline prompt (including element-source proposals for architecture and adaptive diagrams), optional-output validation, persistence, and attached-agent guidance. Normalize existing sequence, call-flow, and glossary references into the shared evidence contract; validate new element bindings through each adapter and briefing hydration. Add focused regeneration with existing concurrency and receipt rules. Do not add a normal-path agent round trip.

Exit: both standalone and attached transports accept the contract; invalid narrative leaves the valid tour usable; stale in-flight work cannot overwrite the current document.

3 · Persistent reader

Replace the modal with a Briefing view.

Wire the Briefing tab, rename the existing visible Diff label to Changes, and integrate the section outline, interleaved block renderer, diagram adapters, landing rules, preference migration, and loading / fallback / outdated states. Reuse the current themes. Implement the right-pane shell and keep attention/effort outside the central document, including legacy fallbacks.

Exit: a reviewer can explain the change from the document alone, with or without diagrams. No tool form, source inspector, findings list, or effort widget is mounted in the center. Legacy intro links and disabled auto-opening behave as specified.

4 · Evidence and questions

Connect each explanation to investigation.

Add native text-selection actions, whole-diagram and element selection, removable context chips, and immutable question snapshots. Host the existing sequence code-step stack in the right pane. All steps remain visible in authored order; diagram selection reveals and highlights the corresponding card, and card selection synchronizes the diagram. 05 · Acceptance and risks

What must hold before this is the default.

  • Clarity: a reader can identify the motivation, changed behavior, main responsibilities, and relevant boundaries without opening the code tour. Sections have descriptive titles, not filenames.
  • Provenance: stated intent names its source; inferred rationale is labeled; source excerpts match captured old/new blobs exactly. Narrative gaps remain visible.
  • Boundary clarity: maps name responsibility owners and crossing data/contracts, distinguish observed structure from inferred rationale, and make no unsupported process/trust/deployment guarantees. Reuse the existing architecture artifact and preference/fallback behavior.
  • Proportionality: a small change gets a short explanation. A complex change includes only diagrams that support a particular section. Missing diagrams do not prevent understanding.
  • Clean center: the center contains only the authored narrative, its diagrams/examples, and lightweight citations/actions. Questions, chips, source previews, review status, and their loading/error states remain in the right pane or existing review tabs, including on mobile and in old-session fallbacks.
  • Navigation: source inspection leaves tour and review progress intact. Opening/resizing/closing the inspector preserves the visible reading anchor. Return, browser reload/resume, and unrelated session updates preserve reading state where the saved document still matches.
  • Selected context: text selections across formatting/blocks and whole-diagram/message selections become visible, removable chips in the right-hand question composer. Combining text and a diagram preserves both. Keyboard/touch selection, cancellation, draft restoration, and post-regeneration stale handling are exercised.
  • Context ownership: inspect a sequence → ask about the boundary diagram → evidence contains only that boundary’s linked sources, with the correct header and no sequence step list. Exercise the reverse transition, source citations, section/text questions, missing evidence, two embeddings of one artifact, and out-of-order responses. Composer context remains explicit, inspectable, and unchanged by inspection alone; collapsing/reopening retains the draft.
  • Diagram-source parity: when a sequence is being inspected, the right pane retains code cards for all its messages in authored order, with all saved supporting excerpts. Message selection highlights/reveals its card; card selection updates the same diagram; free scrolling does not change the selection. Missing-evidence cards keep their place. 06 · Defaults to review

The proposal’s key decisions

Briefing and Changes sit alongside each other. Briefing is the new reading view. Changes is the agreed label for the current Diff workspace, retaining its existing code-review behavior and internal view identity.

Keep the center exclusively for the briefing. Source inspection, questions, selected context, and review tools belong in the right pane. Selecting a sequence step highlights its code in the complete, vertically stacked list there; opening Changes is optional. Use the existing Briefing tab to return from Changes. The composer needs no “Back to reading” button, and same-page actions use no external-link arrows.

The right pane follows the item being inspected. Replace the independent Source / Questions tabs with evidence and a composer in one pane. Asking about a boundary diagram shows that diagram’s evidence, never the previous sequence’s code stack. The draft’s explicit context chips remain separately visible and inspectable.

Explain boundaries visually when useful. Reuse an architecture map to show who owns each responsibility and what crosses between owners. Components and their code cards select each other, and component questions carry the exact node’s evidence. Evidence determines whether a boundary is organizational, process, trust, or simply a code responsibility; the diagram must not imply guarantees the source does not establish.

Generate with the existing outline. Keep launch behavior stable in v1. Decoupling the briefing from detailed tour preparation is a later optimization.

Let readers select their question context. Select text, a whole diagram, or a supported diagram step/element. Add or remove context chips in the right-hand question composer before sending; the question keeps its captured source and exact selection.

Make evidence a shared diagram capability. Sequence steps, architecture components/relationships, lifecycle states/transitions, data entities/relationships, call flows, and domain concepts use one inspector and evidence contract with family adapters. Reuse existing exact mappings and add validated references where missing. Code and document snippets stay associated with the correct element; elements without verified evidence remain explicitly unlinked. Structured blocks add prose and navigation around these interactive artifacts.

Keep both review depths. The briefing explains intent and design; the detailed tour remains the path through exact implementation evidence.
